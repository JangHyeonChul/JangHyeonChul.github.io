구조부터 채점, 회원 · 게시판, 이메일 인증까지 개발한 기능을 순서대로 정리했다. 그림은 개발하면서 직접 그린 다이어그램이다.

## 프로젝트 구조와 요청 흐름

### 패키지 구조

코드를 쓰기 시작하면서 제일 먼저 정한 건 패키지 구조였다.
기준은 하나였다. 다른 사람이 처음 이 프로젝트를 열어봐도 어떤 기능이 어디 있는지 바로 찾을 수 있어야 한다.

![IntelliJ에서 본 패키지 구조. algoproject 아래 compiler, config, controller, dto, mapper, security, service, serviceimpl, validator 패키지와 PageHandler, Time 클래스가 있다](/covers/algorithm-server/dev/package-tree.png)

그래서 비슷한 관심사를 가진 클래스끼리 묶는 계층형 구조로 나눴다.

![패키지별 역할. Compiler는 컴파일 수행, Config는 자주 쓰는 상수, Controller는 요청 처리와 관리자 페이지 컨트롤러, DTO는 계층 간 데이터 이동 객체, Mapper는 데이터베이스 매퍼, Security는 Spring Security, Service는 서비스 인터페이스, ServiceImpl은 그 구현체, Validator는 유효성 검사를 맡는다](/covers/algorithm-server/dev/package-layers.png)

| 패키지 | 맡은 일 |
|---|---|
| `controller` | 요청을 받아 서비스로 넘기고 화면을 돌려준다. 관리자 페이지 컨트롤러는 `admin` 아래로 따로 뺐다 |
| `service` · `serviceimpl` | 비즈니스 로직. 인터페이스와 구현체를 나눴다 |
| `mapper` | MyBatis 매퍼. SQL은 XML에 둔다 |
| `dto` | 계층 사이에서 데이터를 옮기는 객체 |
| `compiler` | 언어별 컴파일과 채점 |
| `security` | 로그인 처리와 권한 설정 |
| `validator` | 회원가입, 게시글, 비밀번호 변경 같은 입력값 검증 |
| `config` | 권한 이름, 채점 결과, 글자 수 제한 같은 상수 |

구조를 잡으면서 좀 더 나은 방법이 없나 찾아보다가 레이어드 아키텍처 패턴을 알게 됐다.

### 요청 흐름

사용자가 사이트에 들어와서 할 수 있는 일을 컨트롤러 기준으로 그려보면 이렇다.

![전체 요청 흐름. 사용자가 HomeController로 사이트에 들어와 RegisterController에서 회원가입하고 LoginController로 로그인한다. 로그인 후에는 ProblemController(문제 풀기), BoardController(게시판), MypageController(마이페이지)로 가고, 관리자는 AdminController를 거쳐 AdminNotificationController(공지 등록)와 AdminProblemController(문제 등록)로 간다](/covers/algorithm-server/dev/request-flow.png)

회원가입을 하고 로그인하면 문제 풀기, 게시판, 마이페이지를 쓸 수 있다.
관리자 권한을 가진 계정은 관리자 페이지에서 공지사항과 문제를 등록한다.

로그인할 때 권한 확인과 비밀번호 검증은 Spring Security가 맡는다.
DB에 암호화되어 저장된 비밀번호를 찾아 입력값과 맞는지 확인하고, 맞으면 그 회원의 권한을 붙여준다.
권한은 미인증, 인증, 관리자 세 가지로 나눴고, 주소마다 어떤 권한이 필요한지는 설정 한 곳에 모아 뒀다.

```java
// /admin 아래는 관리자만
.requestMatchers("/admin/**").hasAnyAuthority(ROLE_ADMIN)
// 제출 내역, 문제 제출, 글쓰기는 이메일 인증을 마친 회원부터
.requestMatchers("/history/**", "/challenge/**", "/board/write")
    .hasAnyAuthority("ROLE_ADMIN", "ROLE_USER")
// 나머지는 모두 허용
.requestMatchers("/**").permitAll()
```

컨트롤러는 관리자용 3개를 포함해 16개가 됐다. 아래부터는 그중에서 가장 손이 많이 갔던 기능들을 하나씩 정리한다.

## 채점 — 사용자 코드를 서버에서 컴파일하기

### 가장 고민했던 기능

알고리즘 검증 사이트를 만들면서 가장 고민됐던 건 "사용자의 코드를 어떻게 검증할까"였다.
백준 운영자분이 쓴 "BOJ는 어떻게 만들어졌을까?"를 참고해서 방법을 잡았다.
서버에 문제마다 여러 개의 모범 출력을 저장해 두고, 사용자가 제출한 프로그램을 컴파일한 뒤 서버에 저장된 정답과 하나씩 비교한다. 하나라도 틀리면 오답이다.

이걸 한 번에 만들려고 하면 막막해서, 하고 싶은 걸 작은 단위로 쪼갰다.

1. 사용자가 입력한 코드를 서버로 보낸다.
2. 받은 코드를 선택한 언어의 파일로 만든다.
3. 그 파일을 컴파일하고 실행해서 출력을 얻는다.
4. 출력을 테스트 케이스의 정답과 비교한다.
5. 결과를 저장하고 포인트를 준다.

### 1. 코드 편집기

첫 단계는 코드를 서버로 보내는 거였다. 이 과정에서 백준이 쓰고 있는 CodeMirror라는 코드 편집기를 알게 되어 클라이언트에 붙였다.
언어를 고르면 그 언어의 기본 소스 템플릿을 띄워줘서, 사용자가 `main` 함수부터 다시 쓸 필요가 없게 했다.

![문제 풀기 화면. 언어 선택(JAVA), 소스 템플릿(JAVA · C · PYTHON), Java 기본 코드가 들어간 CodeMirror 편집기와 제출하기 버튼, 그 아래 문제 상세 설명이 있다](/covers/algorithm-server/dev/code-editor.png)

### 2~4. 컴파일하고 비교하기

채점 전체 흐름은 이렇게 그렸다.

![채점 순서도. 문제 제출 준비에서 제출 권한이 있는지 확인하고, 알고리즘을 입력받아 DB에 저장된 문제의 테스트 케이스를 전부 가져온다. 컴파일이 제대로 되는지, 테스트 케이스의 값들과 일치하는지 확인한 뒤 유저 포인트를 적립하고, 결과 정보를 히스토리에 저장한다](/covers/algorithm-server/dev/judge-flow.png)

제출된 코드는 서버에서 받아, 언어에 맞는 컴파일러와 인터프리터(Java는 JDK, C는 gcc, Python은 Python 인터프리터)가 실행한다.
테스트 케이스는 DB에 여러 개 담아 두고, 케이스마다 결과를 세 가지 중 하나로 매긴다.

| 결과 | 뜻 |
|---|---|
| Error | 컴파일 에러 |
| Success | 테스트 케이스 통과 |
| Fail | 테스트 케이스 실패 |

케이스별 결과를 List에 담은 다음, 하나라도 Fail이 있으면 실패, 전부 Success면 성공으로 판정한다.
컴파일 에러가 나면 남은 테스트 케이스를 돌릴 이유가 없으니 바로 빠져나와 에러를 보여준다.

Java는 `JavaCompiler`로 직접 컴파일하고, C와 Python은 서버에 설치된 gcc와 Python을 프로세스로 띄워 실행했다.
언어마다 어떻게 실행하고 입출력을 맞췄는지는 [다음 글](/projects/algorithm-server/05-compile-by-language/)에 따로 정리했다.

### 5. 결과 저장과 포인트

코드를 제출하면 제출 내역 테이블(Solve History)에 기록된다.
제출 번호를 기본키로 두고, 회원 아이디와 문제 번호를 외래키로, 제출 일자, 성공 여부, 제출 언어를 함께 저장해 화면에 보여준다.

문제를 맞히면 처음 한 번만 포인트가 적립되고, 해결한 문제 테이블(Solve)에 문제 번호와 아이디가 저장된다.
해결한 문제는 계속 다시 도전할 수 있지만, 그 뒤에 또 맞혀도 포인트는 다시 주지 않는다.

여기서 포인트 적립, 해결한 문제 저장, 제출 내역 저장 세 가지가 모두 DB를 바꾼다.
중간에 예상치 못한 오류가 나서 하나만 반영되면 데이터가 어긋나기 때문에, `@Transactional`로 묶어서 셋이 함께 성공하거나 함께 취소되게 했다.

### 나중에 보강한 것: 악성 코드 막기

채점 사이트는 결국 모르는 사람이 보낸 코드를 내 서버에서 실행하는 서비스다.
그래서 2023년 8월 보강 작업 때 잘못된 코드가 넘어오는 걸 막는 방지책을 몇 가지 더 붙였다.

- **글자 수 제한.** 코드는 1,000자까지만 받는다. 비정상적으로 긴 코드가 컴파일되는 걸 막고, 덤으로 코드를 짧게 고민하게 만드는 효과도 있다.
- **특정 단어 필터링.** `exit`, `runtime`, `download`처럼 알고리즘 풀이에 필요 없는 단어가 들어 있으면 채점하지 않는다.
- **계정 차단.** 필터링에 걸린 코드는 악의가 있다고 보고, 일정 횟수를 넘기면 차단한다.
- **컴파일 서버 분리.** 웹 서버에는 DB 정보와 설정이 다 들어 있어서, Java 채점은 컴파일만 하는 서버로 떼어냈다.

## 회원가입 · 로그인, 게시판, 입력값 검증

### 회원가입 · 로그인

![회원가입 · 로그인 흐름. RegisterController가 회원정보를 받으면 RegisterValidator가 유효성을 검사하고, 통과하면 Spring Security가 비밀번호를 암호화해 DB에 저장한다. 로그인은 LoginController에서 MemberDetailService로 넘어가 아이디와 비밀번호가 맞는지 확인하고, 맞으면 SecurityContextHolder에 세션을 저장해 로그인을 끝낸다](/covers/algorithm-server/dev/register-login.png)

회원가입을 하면 아이디, 이메일, 닉네임, 비밀번호, 상태 메시지가 회원 테이블에 저장된다.
저장하기 전에 서버에서 값이 올바른지 먼저 검사한다.

- 이메일 형식이 맞는지
- 닉네임이 2글자 이상인지
- 비밀번호와 비밀번호 확인이 같은지
- 비어 있는 값은 없는지
- 이미 쓰는 아이디 · 이메일 · 닉네임은 아닌지

올바르지 않은 값이 있으면 ErrorMap에 오류 메시지를 담아 사용자에게 보여준다.
ErrorMap이 비어 있으면 그 회원 객체를 Spring Security에 넘겨 비밀번호를 암호화하고 DB에 저장한다.

처음 가입하면 미인증 권한을 받는다. 이 상태에서는 글쓰기, 댓글 작성, 문제 도전이 막혀 있다.
로그인을 하지 않았을 때도 해당 주소로는 들어갈 수 없다.

| 권한 | 이름 |
|---|---|
| 미인증 회원 | `ROLE_UNAUTH` |
| 인증 회원 | `ROLE_USER` |
| 관리자 | `ROLE_ADMIN` |

### 게시판

![게시판 흐름. BoardController에서 로그인 여부와 권한을 확인한 뒤 게시물을 작성한다. BoardService가 태그, 댓글 금지, 사용 언어 입력을 받아 BoardValidator로 제목 길이와 공백을 검사하고, 통과하면 게시물을 등록한다](/covers/algorithm-server/dev/board-flow.png)

게시판은 먼저 로그인했는지, 그리고 이메일 인증을 마친 회원인지 확인한다.
글을 쓰면 BoardService를 통해 등록하기 전에 BoardValidator가 제목이 비어 있는지, 너무 길지는 않은지 검사한 뒤 등록한다.
글을 쓸 때는 카테고리(질문 · 자유 · 강의 · 문제)와 사용 언어를 고를 수 있고, 댓글을 막아둘 수도 있다.

글 수정과 삭제는 작성자 본인만 할 수 있게, 요청한 사람의 아이디와 글쓴이의 아이디가 같은지 확인한다.

### 마이페이지

![MypageController가 맡는 기능. 회원정보 수정, 비밀번호 변경, 이메일 인증, 내가 쓴 게시물, 정보, 알림](/covers/algorithm-server/dev/mypage.png)

마이페이지에서는 회원 정보 수정, 비밀번호 변경, 이메일 인증, 내가 쓴 게시물, 내 정보, 알림을 볼 수 있다.
탭을 누를 때마다 화면 전체를 다시 불러오지 않고, 필요한 데이터만 받아와서 바꾸게 했다.

비밀번호 변경은 클라이언트에서 한 번, 서버에서 한 번 더 검사한다.
클라이언트 검사는 사용자가 얼마든지 우회할 수 있기 때문에, 서버 검사를 통과해야만 바꾸고 성공 여부를 메시지와 함께 돌려준다.

### 입력값 검증과 오류 메시지

회원가입, 게시글, 비밀번호 변경처럼 값을 받는 곳마다 검증이 필요해서, 검증 로직만 따로 모아 validator 패키지로 뺐다.

![validator 구조. BoardValidator(게시물 유효성 검증기), MypagePassword(비밀번호 변경 유효성 검증기), RegisterValidator(회원가입 유효성 검증기)](/covers/algorithm-server/dev/validators.png)

각 검증기는 공백 여부, 중복, 글자 수 제한 같은 검사를 맡는다.
검증기에서 쓰는 오류 메시지는 코드 안에 직접 쓰지 않고 `errors.properties` 한 곳에서 관리했다.

![errors.properties 일부. 필수 입력, 중복 체크, 최소 글자 수, 재확인, 입력값 초과, 기본 메시지로 나뉘어 있고, 예를 들어 duplication.user_id는 "이미 존재하는 아이디 입니다", length.user_nickname은 "닉네임은 {0}글자 이상이어야 합니다"](/covers/algorithm-server/dev/error-messages.png)

메시지를 한 곳에 모아 두니, 문구를 바꾸거나 새 메시지를 추가할 때 이 파일만 고치면 됐다.
`{0}` 자리에 최소 글자 수 같은 값을 끼워 넣을 수 있어서, 숫자가 바뀌어도 메시지를 따로 고칠 필요가 없다.

## 이메일 인증과 @Async

### 요구사항부터

이메일 인증은 바로 코드를 짜지 않고, 먼저 요구사항을 적어봤다.

1. 이메일 인증은 마이페이지의 이메일 인증 탭에서 한다.
2. 인증 링크는 발송 후 30분이 지나면 만료된다.
3. 만료되면 다시 발급받아야 한다.
4. 재발급은 서버에서 정한 5번까지만 할 수 있고, 넘으면 일정 시간이 지난 뒤 초기화된다.
5. 링크를 보낼 때마다 시도 횟수가 하나씩 쌓인다.
6. 인증에 성공하면 이메일 탭이 인증 완료 화면으로 바뀐다.
7. 인증이 끝나면 더 이상 인증 링크를 보낼 수 없다.

이렇게 적어놓고, 다시 기능을 작게 잘라서 하나씩 구현했다.

### 구현

![이메일 인증 순서도. 사용자가 이메일 인증 페이지에서 인증을 요청하면 시도 횟수가 5를 넘는지 확인한다. 넘지 않으면 만료 시간, 발급 일자, 토큰을 갱신하고, 링크를 눌렀을 때 만료 시간이 지나지 않았으면 유저 권한을 갱신해 이메일 인증을 완료한다](/covers/algorithm-server/dev/email-flow.png)

처음에는 이 회원이 이메일 인증을 처음 시도하는지 확인한다.
이메일 인증 토큰 테이블(만료 시간, 발급 시간, UUID, 회원 아이디)에 그 회원의 아이디가 없으면 새로 만든다.

이미 있으면 UPDATE로 시도 횟수를 1 올리고, 5번을 넘었는지 확인한다.
넘지 않았으면 메일을 보내면서 만료 시간, 발급 시간, UUID를 새로 갱신한다.

메일에 들어가는 인증 링크에는 UUID와 회원 아이디를 쿼리스트링으로 붙였다. 링크를 누르면 두 가지를 검사한다.

1. 만료 시간이 지났는지
2. 토큰 값이 같은지

하나라도 맞지 않으면 오류 화면으로 보내서 다시 요청하라고 알려준다.
둘 다 통과하면 회원 권한을 인증 회원으로 바꾸고, 그때부터 글쓰기와 문제 제출을 할 수 있다.

### 3~5초씩 멈추던 메일 발송

여기서 발목을 잡은 건 메일 발송이었다. 구글 SMTP로 메일을 보내면, 발송이 끝날 때까지 3~5초 동안 화면이 로딩 상태로 멈춰 있었다.

혼자 보낼 때는 참을 만했지만, 여러 사람이 동시에 메일을 요청하면 더 길어질 수 있겠다는 생각이 들었다.
학부 때 배운 병렬 처리를 떠올리면서 Spring Boot에서는 이걸 어떻게 쉽게 쓸 수 있는지 찾아봤고, 메서드에 `@Async`만 붙이면 별도 스레드에서 실행된다는 걸 알게 됐다.

적용하고 나니 인증 메일을 요청하자마자 처리 메시지가 바로 떴고, 메일이 가는 동안에도 페이지에서 다른 걸 할 수 있었다.
메일 발송을 맡은 스레드가 일을 마치면 메일이 도착하니까, 사용자 입장에서는 훨씬 빠르게 느껴졌을 것 같다.

다만 이 부분은 유용하지만, 어노테이션 하나로 끝내기보다는 더 공부해야겠다는 생각이 들었다.
