## 가장 고민했던 기능

알고리즘 검증 사이트를 만들면서 가장 고민됐던 건 "사용자의 코드를 어떻게 검증할까"였다.
백준 운영자분이 쓴 "BOJ는 어떻게 만들어졌을까?"를 참고해서 방법을 잡았다.
서버에 문제마다 여러 개의 모범 출력을 저장해 두고, 사용자가 제출한 프로그램을 컴파일한 뒤 서버에 저장된 정답과 하나씩 비교한다. 하나라도 틀리면 오답이다.

이걸 한 번에 만들려고 하면 막막해서, 하고 싶은 걸 작은 단위로 쪼갰다.

1. 사용자가 입력한 코드를 서버로 보낸다.
2. 받은 코드를 선택한 언어의 파일로 만든다.
3. 그 파일을 컴파일하고 실행해서 출력을 얻는다.
4. 출력을 테스트 케이스의 정답과 비교한다.
5. 결과를 저장하고 포인트를 준다.

## 1. 코드 편집기

첫 단계는 코드를 서버로 보내는 거였다. 이 과정에서 백준이 쓰고 있는 CodeMirror라는 코드 편집기를 알게 되어 클라이언트에 붙였다.
언어를 고르면 그 언어의 기본 소스 템플릿을 띄워줘서, 사용자가 `main` 함수부터 다시 쓸 필요가 없게 했다.

## 2~4. 컴파일하고 비교하기

채점 전체 흐름은 이렇게 그렸다.

![채점 순서도. 문제 제출 준비에서 제출 권한이 있는지 확인하고, 알고리즘을 입력받아 DB에 저장된 문제의 테스트 케이스를 전부 가져온다. 컴파일이 제대로 되는지, 테스트 케이스의 값들과 일치하는지 확인한 뒤 유저 포인트를 적립하고, 결과 정보를 히스토리에 저장한다](/covers/algorithm-server/dev/judge-flow.png)

제출된 코드는 서버에서 받아, 언어에 맞는 컴파일러와 인터프리터(Java는 JDK, C는 gcc, Python은 Python 인터프리터)가 실행한다.
테스트 케이스는 DB에 여러 개 담아 두고, 케이스마다 결과를 세 가지 중 하나로 매긴다.

| 결과 | 뜻 |
|---|---|
| Error | 컴파일 에러 |
| Success | 테스트 케이스 통과 |
| Fail | 테스트 케이스 실패 |

케이스별 결과를 List에 담은 다음, 하나라도 Fail이 있으면 실패, 전부 Success면 성공으로 판정한다.
컴파일 에러가 나면 남은 테스트 케이스를 돌릴 이유가 없으니 바로 빠져나와 에러를 보여준다.

### Java

[이 글](https://clamp83.tistory.com/217)을 참고해서 Java부터 만들었다.
먼저 `.java` 파일을 만들고 사용자에게 받은 소스 코드를 붙여넣는다. 그다음 Java가 제공하는 `JavaCompiler`로 컴파일하고, 컴파일된 클래스를 불러와 인스턴스를 로드한다.
로드한 클래스의 `main` 메서드를 실행해서 나온 출력값을 정답값으로 보고, DB에 저장된 모범 출력과 비교해 정답 처리했다.

만들고 나서 아쉬웠던 점이 있다. 출력(`println`)으로 정답을 확인하다 보니 사용자가 답을 내는 방식의 자유도가 너무 떨어졌다.
차라리 메서드가 `return`한 값을 정답으로 쓰는 편이 더 좋았겠다는 생각이 들었다.

### C · Python

Java는 언어 안에 컴파일러가 있어서 비교적 쉬웠는데, 문제는 다른 언어였다. Java 안에서 다른 언어를 컴파일해 본 적이 처음이었기 때문이다.

우선 C 컴파일러인 gcc가 어떻게 컴파일하는지부터 봤다. 결국 Java 때와 비슷했다.
`.c` 파일을 만들어 소스 코드를 넣고, gcc 명령어로 그 파일을 컴파일해 달라고 요청하면 된다.
컴파일러를 설치한 뒤 `.c` 파일을 만들고 gcc로 컴파일, 실행 결과의 표준 출력을 가져와 테스트 케이스를 돌려 정답 처리하는 순서로 만들었다.
Python도 같은 방식으로 파일을 만들고 인터프리터 프로세스를 띄워 표준 출력을 받았다.

## 5. 결과 저장과 포인트

코드를 제출하면 제출 내역 테이블(Solve History)에 기록된다.
제출 번호를 기본키로 두고, 회원 아이디와 문제 번호를 외래키로, 제출 일자, 성공 여부, 제출 언어를 함께 저장해 화면에 보여준다.

문제를 맞히면 처음 한 번만 포인트가 적립되고, 해결한 문제 테이블(Solve)에 문제 번호와 아이디가 저장된다.
해결한 문제는 계속 다시 도전할 수 있지만, 그 뒤에 또 맞혀도 포인트는 다시 주지 않는다.

여기서 포인트 적립, 해결한 문제 저장, 제출 내역 저장 세 가지가 모두 DB를 바꾼다.
중간에 예상치 못한 오류가 나서 하나만 반영되면 데이터가 어긋나기 때문에, `@Transactional`로 묶어서 셋이 함께 성공하거나 함께 취소되게 했다.

## 나중에 보강한 것: 악성 코드 막기

채점 사이트는 결국 모르는 사람이 보낸 코드를 내 서버에서 실행하는 서비스다.
그래서 2023년 8월 보강 작업 때 잘못된 코드가 넘어오는 걸 막는 방지책을 몇 가지 더 붙였다.

- **글자 수 제한.** 코드는 1,000자까지만 받는다. 비정상적으로 긴 코드가 컴파일되는 걸 막고, 덤으로 코드를 짧게 고민하게 만드는 효과도 있다.
- **특정 단어 필터링.** `exit`, `runtime`, `download`처럼 알고리즘 풀이에 필요 없는 단어가 들어 있으면 채점하지 않는다.
- **계정 차단.** 필터링에 걸린 코드는 악의가 있다고 보고, 일정 횟수를 넘기면 차단한다.
- **컴파일 서버 분리.** 웹 서버에는 DB 정보와 설정이 다 들어 있어서, Java 채점은 컴파일만 하는 서버로 떼어냈다.
