## 시작은 "이걸 직접 만들 수 있을까?"였다

프로젝트를 고를 때 처음 떠오른 건 백준이나 프로그래머스 같은 알고리즘 채점 사이트였다.
문제를 풀어서 제출하면 몇 초 만에 맞았는지 틀렸는지 알려주는데, 그 몇 초 사이에 서버에서 무슨 일이 일어나는지 궁금했다.
남이 짠 코드를 내 서버에서 컴파일하고 실행한다는 게 막연하게 어려워 보였고, 그래서 더 해보고 싶었다.

거기에 프로그래머스에서 본 기능이 하나 더 눈에 들어왔다. 문제를 풀면 포인트가 쌓이고, 그 포인트로 다른 사람과 순위를 겨루는 것이다.
그래서 채점 구조는 백준을 모티브로 삼고, 포인트와 랭킹은 프로그래머스처럼 붙여보기로 했다.

만들고 싶은 기능을 적어보니 금방 길어졌다.
문제 목록(난이도 상·중·하, 알고리즘 종류), 코드 제출과 채점(Java·C·Python), 포인트와 랭킹, 제출 내역, 게시판, 이메일 인증, 관리자 페이지까지.
"이걸 혼자 3개월 안에 다 할 수 있을까?" 싶었지만, 일단 해보기로 했다.

## 백준은 코드를 어떻게 채점할까

제일 먼저 막힌 건 채점이었다. 사용자 코드를 어떻게 검증해야 할지 감이 오지 않았다.
그래서 백준 운영진이 직접 쓴 글부터 찾아 읽었다.
「BOJ 10 Years」 시리즈에 백준의 구조가 바뀌어 온 과정이 자세히 나와 있는데, 지금 구조를 간단히 그려보면 이렇다.

읽으면서 재밌었던 건 백준도 처음부터 이 모양이 아니었다는 점이다.
2010년에는 서버 한 대에 웹과 채점이 같이 있었고, 채점 프로그램이 1초마다 DB를 뒤져서 채점할 소스를 찾았다고 한다.
제출이 늘면서 채점 서버를 두 대로 늘려 채점 번호 홀수·짝수로 나눠 맡겼고, AWS로 옮기면서 큐(SQS)를 두어 홀짝 구분을 없앴다.
테스트 데이터도 처음에는 웹 서버에서 파일로 만들어 채점 서버로 보냈는데, 서버가 늘어나면서 채점 서버가 미리 받아 두는 방식으로 바뀌었다.

이 과정을 보고 채점의 핵심은 생각보다 단순하다는 걸 알았다.
문제마다 테스트 케이스의 정답 출력을 저장해 두고, 제출된 코드를 컴파일해서 실행한 다음, 출력을 하나씩 비교한다. 하나라도 틀리면 오답이다.
나머지 복잡한 구조는 전부 제출이 많아졌을 때 버티기 위해 나중에 붙은 것이었다.

그래서 나는 백준의 맨 처음 모습에서 시작하기로 했다. 웹 서버 한 대 안에서 제출을 받고, 바로 컴파일하고, 테스트 케이스와 비교한다.
사용자가 몰리는 서비스를 만들려는 게 아니었기 때문에, 큐나 채점 서버 분리보다는 채점이 제대로 돌아가는 것 자체가 먼저라고 판단했다.

## 이 프로젝트로 얻고 싶었던 것

**서비스 하나를 처음부터 끝까지 혼자 만들어보기.**
회원가입부터 권한, 채점, 게시판, 배포(AWS EC2·RDS)까지, 빈 화면에서 시작해서 실제로 쓸 수 있는 사이트가 되는 과정을 한 번은 혼자 끝까지 겪어보고 싶었다.

**남의 코드를 내 서버에서 돌리는 방법.**
채점 사이트를 고른 가장 큰 이유다. Java는 자바가 제공하는 컴파일러로, C는 gcc로, Python은 인터프리터로 실행해야 하는데, 언어마다 방법이 다르다.
자바 안에서 다른 언어를 컴파일해 본 적이 없어서 여기서 제일 많이 배울 거라고 생각했다.

**데이터베이스를 제대로 설계해보기.**
문제, 제출 내역, 해결한 문제, 포인트, 게시판처럼 서로 얽힌 테이블이 많았다.
정규화나 인덱스, 트랜잭션, Lock 같은 말은 들어봤지만 내 설계에 직접 적용해 본 적은 없었다.
그래서 『데이터베이스 개론』을 읽으면서 하나씩 정리하고 설계에 반영해보기로 했다.

**남에게 설명할 수 있는 코드.**
내가 만든 로직은 항상 남에게 설명할 수 있어야 한다고 생각한다.
그래서 구현하기 전에 로직을 메모장에 먼저 적고, 패키지 구조도 다른 사람이 봤을 때 어떤 기능이 어디 있는지 바로 찾을 수 있게 잡는 걸 목표로 했다.

필요한 내용은 인프런과 패스트캠퍼스 강의, 그리고 『Effective Java』와 『리팩터링』을 읽으면서 채웠다.
기간은 2023년 2월부터 5월까지 3개월, 혼자 진행했다.
