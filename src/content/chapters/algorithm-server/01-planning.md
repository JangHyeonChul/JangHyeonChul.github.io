## 시작점 — "제출" 버튼 뒤가 궁금했다

백준이나 프로그래머스에서 제출을 누르면, 몇 초 뒤에 "맞았습니다"가 뜹니다.
그 몇 초 사이에 무슨 일이 일어나는지 궁금했습니다.

- 내가 쓴 코드는 **어디서** 컴파일되는가
- 그 서버는 내가 **무슨 짓을 하든** 괜찮은가

두 번째 질문이 이 프로젝트의 진짜 동기였습니다.
생각해보면 이상한 일입니다. 온라인 저지는 처음 보는 사람이 보낸 코드를
자기 서버에서 **실행해야만** 채점할 수 있습니다.

> 온라인 저지는 임의 코드 실행(RCE)을 *기능으로* 제공하는 서비스다.

보통은 막아야 할 것을 서비스의 핵심으로 제공한다면, 그 경계는 어떻게 설계되어 있을까.
직접 만들어보는 것 말고는 알 방법이 없었습니다.

## 무엇을 만들 것인가

저지의 최소 형태를 잡았습니다.

| 영역 | 내용 |
|---|---|
| 인증 | 회원가입, 이메일 토큰 인증(JavaMailSender), Spring Security |
| 문제 | 관리자 문제 등록·수정, 테스트케이스(입력/출력) 관리 |
| 채점 | Java / C / Python 제출 → 컴파일 → 테스트케이스 대조 |
| 동기 부여 | 정답 시 포인트 지급, 랭킹 |
| 커뮤니티 | 게시판, 댓글, 알림 |

이 중 **채점**만이 이 프로젝트를 다른 CRUD 토이 프로젝트와 다르게 만듭니다.
나머지는 익숙한 문제였고, 채점은 처음 보는 문제였습니다.

## 처음 그린 채점 흐름

```text
[브라우저]  코드 + 언어 + 문제번호
     │
     ▼
[웹 서버]  CompileValidator  ← 여기서 먼저 거른다
     │
     ▼
          CompileService
     │         ├ JAVA   ── HTTP POST ──▶ [컴파일 서버 :8081]
     │         ├ C      ── 프로세스 실행
     │         └ PYTHON ── 프로세스 실행
     ▼
  테스트케이스 input/output 대조 (하나라도 틀리면 실패)
     │
     ▼
  채점 이력 저장 + 포인트 지급   @Transactional
```

문제의 정답 케이스를 DB에서 꺼내 **개수만큼 반복 실행**하고,
결과 리스트에 에러가 하나라도 있으면 `compile error`,
실패가 하나라도 있으면 `fail`, 전부 통과해야 `success`로 처리했습니다.

## 이때 내린 결정들

| 결정 | 이유 | 지금 생각 |
|---|---|---|
| **웹 서버와 컴파일 서버 분리** | 웹 서버에는 DB 접속 정보·설정 같은 민감 데이터가 있다. 남의 코드를 **같은 프로세스에서** 실행하면 그게 전부 사정권에 들어온다 | 만족. 이 프로젝트에서 가장 잘한 결정 |
| MyBatis + 직접 쓴 SQL | 인덱스·트랜잭션·Lock을 눈으로 보고 싶었음 | 만족. 공부 목적에는 정확한 선택 |
| 코드 길이 1,000자 제한 | 비정상적으로 긴 코드를 막고, 덤으로 최적화를 유도 | 절반만 만족 |
| 위험 단어 문자열 필터링 | `exit`, `runtime`, `download`가 알고리즘 풀이에 필요 없다고 판단 | **후회.** 아래에서 이야기합니다 |
| 오류 메시지 국제화(`messages.properties`) | 메시지를 한곳에서 관리 | 만족 |

## 보안은 4단으로 막기로 했다

```java
public class CompileValidator {
    private final int CODE_MAXLENGTH = 1000;
    private final String[] FILTER_TEXT = new String[]{ "exit", "runtime", "download" };
    // 길이 초과 또는 금지어 포함 시 false
}
```

1. **글자 수 제한** — 비정상적으로 긴 코드를 컴파일하지 않는다
2. **서버 분리** — 컴파일 서버는 컴파일만 한다. 어떤 데이터도 저장하지 않는다
3. **금지어 필터링** — 프로세스 종료, 런타임 호출, 다운로드 관련 키워드 차단
4. **누적 시 차단** — 필터에 걸린 요청이 반복되면 악의로 보고 계정·IP 차단

설계할 때는 이 네 겹이 꽤 촘촘하다고 생각했습니다.

## 그런데, 이게 이 프로젝트의 진짜 결과물이었다

만들고 나서 내 방어선을 내가 공격해봤습니다. 애초에 그게 궁금해서 시작한 프로젝트였으니까요.

| 내가 막았다고 생각한 것 | 실제로 뚫리는 지점 |
|---|---|
| 금지어 `exit` 필터링 | `getattr(__builtins__, "ex"+"it")` — 문자열을 쪼개면 그만. **블랙리스트는 원리적으로 샌다** |
| 금지어 필터링 (반대 방향) | 변수명이 `runtime_ms`인 정상 코드도 거부된다. 오탐도 같이 늘어난다 |
| 코드 길이 1,000자 | `while True: pass` 는 18자다. **길이는 위험도와 상관이 없다** |
| 서버 분리 | 컴파일 서버에 **타임아웃도 메모리 제한도 없다.** 무한 루프 하나로 프로세스가 점유된다 |
| — | 실행 파일명이 `hello.py` 로 고정. 두 사람이 동시에 제출하면 서로의 코드를 덮어쓴다 |
| — | 컴파일 서버의 **아웃바운드 네트워크가 열려 있다.** 코드 안에서 외부로 요청을 보낼 수 있다 |

목록을 적고 나서야 원래 질문의 답이 보였습니다.
**실제 저지들이 문자열을 필터링해서 막고 있는 게 아니었습니다.**
코드가 무엇을 하든 상관없도록 **실행 환경 자체를 가두는** 방식이어야 했습니다.

## 지금 다시 만든다면

- **블랙리스트 → 샌드박스.** 제출마다 일회용 컨테이너를 띄우고, 끝나면 버린다
- **리소스 상한.** CPU 시간·메모리·프로세스 수·출력 크기를 커널 레벨에서 제한
- **네트워크 차단.** 채점에 외부 통신이 필요할 일은 없다
- **파일 격리.** 제출마다 고유한 작업 디렉터리
- **동기 요청 → 채점 큐.** 지금은 HTTP 요청이 채점이 끝날 때까지 붙잡혀 있다

처음엔 "온라인 저지를 만들어보자"로 시작했는데,
끝나고 보니 **"신뢰할 수 없는 코드를 어떻게 실행할 것인가"** 라는 한 가지 문제였습니다.
위 표가 이 프로젝트에서 가장 값진 결과물입니다.
