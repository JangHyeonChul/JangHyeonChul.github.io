## 기능부터 적었다

설계를 시작하기 전에 만들 기능부터 전부 적어봤다.
테이블을 먼저 그리면 내가 어떤 화면을 만들지도 모르는 채로 컬럼만 늘어날 것 같았다.
그래서 "사용자가 이 사이트에서 무엇을 할 수 있나"를 기준으로 기능을 나누고, 그다음에 그 기능이 어떤 데이터를 읽고 쓰는지 정리하는 순서로 갔다.

적고 보니 크게 다섯 덩어리였다.

| 영역 | 기능 |
|---|---|
| 회원 | 회원가입, 로그인 · 로그아웃, 이메일 인증, 정보 수정, 비밀번호 변경, 프로필 이미지 |
| 문제 · 채점 | 문제 목록(난이도 · 알고리즘 종류별), 문제 보기, 코드 제출과 채점, 제출 내역, 랜덤 문제 |
| 커뮤니티 | 게시판(질문 · 자유 · 강의 · 문제), 댓글, 추천, 내 글에 댓글이 달리면 알림 |
| 경쟁 | 포인트 적립, 랭킹 |
| 관리자 | 문제와 테스트 케이스 등록, 공지사항 등록, 관련 사이트 링크 등록 |

여기에 검색과 공지사항 보기, 이용 방법 페이지 정도가 따라붙었다.

## 누가 무엇을 할 수 있나

기능을 적다 보니 "이건 아무나 하면 안 되겠다" 싶은 것들이 보였다.
문제를 제출하는 건 로그인한 사람만 해야 하고, 문제를 등록하는 건 관리자만 해야 한다.
그런데 가입만 하면 바로 글을 쓸 수 있게 하면, 이메일만 아무렇게나 넣고 도배하는 계정을 막을 방법이 없다.

그래서 권한을 세 단계로 나눴다.

| 권한 | 대상 | 할 수 있는 것 |
|---|---|---|
| `ROLE_UNAUTH` | 가입만 하고 이메일 인증 전 | 문제 보기, 게시판 읽기 |
| `ROLE_USER` | 이메일 인증까지 끝낸 회원 | 코드 제출, 제출 내역, 글 · 댓글 쓰기 |
| `ROLE_ADMIN` | 관리자 | 문제 · 공지사항 · 관련 사이트 등록 |

권한 확인과 비밀번호 검증은 Spring Security에 맡기기로 했다.
비밀번호는 암호화해서 저장하고, 로그인할 때 저장된 값과 맞는지 확인한 뒤 권한을 붙여주는 흐름이다.

## 채점 규칙

채점은 이 사이트의 핵심이라 규칙을 따로 정리해 뒀다.

- 언어는 Java, C, Python 세 가지. 언어를 고르면 기본 소스 템플릿을 띄워준다.
- 문제마다 테스트 케이스를 여러 개 저장해 두고, 제출된 코드의 출력을 하나씩 비교한다.
- 결과는 세 가지다. 컴파일이 안 되면 **Error**, 테스트 케이스를 전부 통과하면 **Success**, 하나라도 틀리면 **Fail**.
- 컴파일 에러가 나면 남은 테스트 케이스는 돌리지 않고 바로 에러를 보여준다.
- 처음 맞힌 문제에만 포인트를 준다. 이미 푼 문제는 다시 풀 수 있지만 포인트는 다시 주지 않는다.

마지막 규칙 때문에 고민이 하나 생겼다.
정답 처리를 하면 포인트 적립, 해결한 문제 기록, 제출 내역 저장까지 테이블 세 곳이 한 번에 바뀐다.
이 중 하나만 실패하면 포인트는 올랐는데 해결 기록은 없는 이상한 상태가 될 수 있다.
그래서 이 세 작업은 하나의 트랜잭션으로 묶기로 했다.

## 이메일 인증 요구사항

권한을 나누고 나니 이메일 인증이 생각보다 신경 쓸 게 많았다. 요구사항을 이렇게 정리했다.

1. 이메일 인증은 마이페이지의 이메일 인증 탭에서 한다.
2. 인증 링크는 발송 후 30분이 지나면 만료된다.
3. 만료되면 다시 발급받아야 한다.
4. 재발급은 5번까지만 할 수 있고, 넘으면 일정 시간이 지난 뒤 초기화된다.
5. 링크를 보낼 때마다 시도 횟수가 하나씩 올라간다.
6. 인증에 성공하면 인증 완료 화면으로 바뀐다.
7. 인증이 끝난 계정에는 더 이상 링크를 보내지 않는다.

4번은 누군가 버튼을 계속 눌러서 메일을 무한정 보내게 만드는 걸 막으려고 넣었다.

## ERD

기능과 권한, 규칙을 정리한 뒤에 테이블을 그렸다. ERD는 ERD Cloud로 만들었다.

![알고리즘 온라인 저지 ERD. 회원, 문제, 문제 답안, 제출 내역, 해결한 문제, 게시판, 댓글, 추천, 알림, 공지사항, 이메일 인증 토큰, 관련 사이트 테이블과 관계](/covers/algorithm-server/erd.png)

전체 ERD는 [ERD Cloud](https://www.erdcloud.com/d/6Te5fmKs5DpDtHL7o)에서 볼 수 있다.

테이블은 13개가 나왔다. 기능 덩어리와 거의 그대로 이어진다.

| 영역 | 테이블 | 담는 것 |
|---|---|---|
| 회원 | 회원 | 아이디, 이메일, 닉네임, 암호화된 비밀번호, 상태 메시지, 포인트, 권한, 등급 |
| | 이메일 인증 토큰 | 토큰(UUID), 발급 시각, 만료 시각, 시도 횟수, 초기화 시각 |
| 문제 · 채점 | 문제 | 제목, 난이도, 알고리즘 종류, 내용, 입출력 설명, 힌트, 맞힌 사람 수 |
| | 문제 답안 | 문제별 테스트 케이스 입력 · 정답 출력 |
| | 제출 내역 | 누가, 어떤 문제를, 언제, 어떤 언어로 냈고 성공했는지, 실패 이유 |
| | 해결한 문제 | 회원과 문제를 잇는 표. 포인트를 한 번만 주는 기준이 된다 |
| 커뮤니티 | 게시판 · 게시판 댓글 · 댓글 게시판 | 글, 카테고리, 조회수, 추천 수, 댓글 |
| | 추천 | 누가 어떤 글을 추천했는지 |
| | 댓글 알림 | 내 글에 달린 댓글과 읽음 여부 |
| 운영 | 공지사항 · 관련 사이트 | 관리자가 올리는 공지와 외부 링크 |

설계하면서 신경 쓴 건 세 가지였다.

**정규화.** 최대한 정규화해서 같은 정보가 여러 곳에 생기는 이상 현상을 막으려고 했다.
회원 한 명은 여러 문제를 풀고, 문제 하나도 여러 회원이 푼다. 이걸 회원 테이블 안에 넣으면 문제를 풀 때마다 회원 행을 고쳐야 하니까, 회원과 문제 사이의 N:N 관계를 해결한 문제 테이블로 따로 뺐다. 추천도 같은 이유로 회원과 게시글 사이의 표로 분리했다.

**인덱스.** 문제 목록은 난이도나 알고리즘 종류로 자주 걸러 보니까 처음엔 거기에 인덱스를 걸려고 했다.
그런데 난이도는 몇 단계뿐이고, 문제 언어도 한국어 · 영어 두 가지뿐이라 카디널리티가 너무 낮았다. 이런 컬럼은 인덱스를 걸어도 걸러지는 양이 적어서 효과가 별로 없다.
그래서 ERD에 "인덱스 안 넣어도 될 것 같음"이라고 메모해 두고, 문제 번호 위주로 가기로 했다.

**관계 표기.** 1:1, 1:N, N:1, N:N을 ERD에 직접 표기하면서, 테이블 사이에 어떤 데이터가 오가는지 한눈에 보이게 하려고 했다.

이 과정에서 인덱스, 트랜잭션, Lock 같은 개념을 『데이터베이스 개론』으로 다시 공부하며 정리했다.

## API 명세

마지막으로 기능을 URL로 옮겼다. 화면을 돌려주는 요청은 GET, 데이터를 바꾸는 요청은 POST · PATCH · DELETE로 나눴다.

| 메서드 | 주소 | 설명 | 권한 |
|---|---|---|---|
| GET | `/problem` | 문제 목록 | 누구나 |
| GET | `/problem/{번호}` | 문제 보기 | 누구나 |
| GET | `/problem/type/{종류}` | 알고리즘 종류별 문제 | 누구나 |
| GET | `/random` | 랜덤 문제로 이동 | 누구나 |
| GET | `/challenge/{번호}` | 코드 작성 화면 | 인증 회원 |
| POST | `/challenge/{번호}` | 코드 제출과 채점 | 인증 회원 |
| GET | `/history/{번호}` | 내 제출 내역 | 인증 회원 |
| GET | `/rank` | 랭킹 | 누구나 |
| GET | `/board` | 게시글 목록 | 누구나 |
| GET | `/board/type/{카테고리}` | 카테고리별 게시글 | 누구나 |
| GET | `/board/page/{번호}` | 게시글 보기 | 누구나 |
| POST | `/board/write` | 게시글 작성 | 인증 회원 |
| PATCH | `/board/update/{번호}` | 게시글 수정 | 작성자 |
| DELETE | `/board/page/{번호}` | 게시글 삭제 | 작성자 |
| POST | `/board/comment` | 댓글 작성 | 로그인 |
| POST | `/board/recommdation` | 게시글 추천 | 로그인 |
| GET · POST | `/register` | 회원가입 | 누구나 |
| GET | `/linkauthentication` | 이메일 인증 링크 확인 | 링크 소지자 |
| POST | `/mypage/email` | 인증 메일 발송 | 로그인 |
| POST | `/mypage/modifyinfo` | 상태 메시지 수정 | 로그인 |
| POST | `/mypage/password` | 비밀번호 변경 | 로그인 |
| GET | `/mypage/alram` | 내 댓글 알림 | 로그인 |
| POST | `/upload` | 프로필 이미지 업로드 | 로그인 |
| GET | `/search`, `/searching` | 검색 화면, 키워드 · 카테고리 검색 | 누구나 |
| POST | `/admin/problem` | 문제 · 테스트 케이스 등록 | 관리자 |
| POST | `/admin/notification` | 공지사항 등록 | 관리자 |
| POST | `/admin/link` | 관련 사이트 등록 | 관리자 |

비밀번호 변경처럼 화면 전체를 다시 그릴 필요가 없는 요청은 결과를 JSON으로 돌려주고, 화면에서 메시지만 바꾸게 했다.
입력값 검증은 클라이언트에서 한 번, 서버에서 한 번 더 하기로 했다. 클라이언트 검증은 사용자가 고칠 수 있기 때문이다.

이렇게 기능 → 권한 → 규칙 → 테이블 → URL 순서로 정리하고 나서야 코드를 쓰기 시작했다.
